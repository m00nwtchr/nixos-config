# Port `~/nixos-config` to the den pattern (aspects)

## Scope

Port the **`tide` host** and its **`m00n` user** (including the full
home config) from `~/nixos-config` (snowfall-lib based) to the den
aspect-oriented pattern already scaffolded at `~/nixnew`. The other
hosts in `nixos-config` (ember, kepler, ganymede, beacon) are
explicitly out of scope; only tide is ported.

The source repo's `nixos-config` itself is broken against current
nixpkgs (it references `boot.binfmtMiscRegistrations` and
`boot.bootMount`, both removed in `nixpkgs 26.11pre`). The den port
is **not** required to evaluate against the same nixpkgs the
source pinned; it will evaluate against whatever nixpkgs the new
flake pulls in.

## Why a markdown plan (not a diff harness)

Previous sessions wasted time building a JSON-diff harness and then
chasing aspect-system recursion bugs. The harness was never the
goal — the port is. We drop the harness. The plan is to port
faithfully and verify by `nix flake check` + `nix build
.nixosConfigurations.tide.config.system.build.toplevel`.

## Decisions (from earlier in this session)

1. **Option paths renamed to den-native.** `m00nlit.hardware.facter.detected.*`
   becomes `den.aspects.facter.detected.*` (the `facter` namespace was
   already registered in the existing `dendritic.nix` via
   `(inputs.den.namespace "hardware" true)` which exposes
   `den.facter.detected.*` — confirmed by reading the existing
   `modules/aspects/hardware/facter.nix`). Documented in
   `MIGRATION.md` at the end.

2. **`pkgsStable` (nixos-25.11) deferred.** The source injects
   `pkgsStable` via `_module.args` in flake.nix. Not needed
   currently (the only consumer — `pkgsStable.librewolf` in
   `homes/.../m00n/default.nix` — is commented out). Documented as
   a follow-up; do not add the `stable` input or the injection
   aspect in this port.

3. **`home.packages` list ordering differences are acceptable.**
   Source has one large list; den splits across multiple imports.
   The diff (whenever we get one) will show reordering. Documented.

4. **`services.easyeffects` preset name uses `{host}` context arg.**
   The source reads `osConfig.networking.hostName` to find the
   per-host easyeffects preset dir. In den, the home-aspect module
   receives `{host, ...}` so we use `host.name` (or whatever the
   den context arg is) and `den.lib.__findFile` to resolve the path.

5. **No `pkgsStable` arg injection, but still **track it** as a
   follow-up** (the TODO comment from the previous plan).

6. **Sops uses the source's `.sops.yaml`** copied verbatim to
   `~/nixnew/.sops.yaml`. The age keys in it cover all hosts (we
   only need tide's). Re-encryption of `secrets/default.yaml` is
   the user's job, not part of the port.

7. **flake-file for new inputs.** Inputs go in
   `modules/dendritic.nix` under `flake-file.inputs`, never
   directly in `flake.nix`. `nix run .#write-flake` regenerates
   `flake.nix`.

## Aspect-system wiring rule

**Lesson from prior session:** the den aspect system has a recursive
type-checker that infinite-loops if you put `den.aspects.*`
declarations inside a `den.aspects.*` that also reads from it. The
existing `modules/aspects/hardware/facter.nix` works, but only
because it uses a sub-aspect (`policies.load-facter`) and doesn't
have nested sub-aspects with cross-references.

To avoid that minefield:

- **All `den.aspects.*` declarations live at the top level of
  their file** (no `den.aspects.system.boot` nesting; just
  `den.aspects.boot`).
- **No `<x/y>` angle-bracket includes in `includes`.** Use
  `imports = [ ./foo.nix ]` instead. The angle-bracket syntax has
  its own resolution rules and namespace-registration requirements
  that we don't need to fight for a 1-host port.
- **Host aspect uses `den.aspects.tide.nixos.imports`** to bring in
  the relevant aspect modules. den walks these as standard NixOS
  imports.
- **User aspect for `m00n` is split:** `users/m00n.nix` declares
  the aspect (`den.aspects.m00n = { ... }` with `homeManager` +
  `includes` batteries); `users/m00n-nixos.nix` is a plain NixOS
  module (m00n user, sops, etc.) imported by the host aspect.
  This avoids the recursive-type issue.
- **No `provides.to-hosts.*` cross-references.** The host aspect
  imports the user NixOS module directly.
- **No `provides.to-users.*` in user aspect.** The host aspect
  sets home packages for the user directly via
  `den.aspects.tide.provides.to-users.homeManager`.

## Order of execution

Do the steps in order. After each step, `nix flake check` (or
`nix eval .#nixosConfigurations.tide.config.system.stateVersion`)
must still succeed. If a step breaks the eval, fix it before
moving on.

1. **Step 0 — baseline & verify.** Confirm `~/nixos-config-baseline/`
   exists; run `nix eval ~/nixos-config-baseline#nixosConfigurations.tide.config.system.stateVersion`
   to confirm the baseline itself evaluates (it should — the
   `stateVersion` path is shallow).

2. **Step 1 — flake inputs.** Edit
   `~/nixnew/modules/dendritic.nix` to add `disko`, `disko-zfs`,
   `sops-nix`, `nixos-hardware`, `zen-browser` under
   `flake-file.inputs`. Leave a `# TODO: re-add stable + pkgsStable
   aspect when librewolf pin is uncommented` comment where `stable`
   would go. Run `nix run .#write-flake && nix flake lock`.

3. **Step 2 — root config files.** Copy verbatim from baseline:
   `.sops.yaml`, `treefmt.toml`, `renovate.json5`, `.gitattributes`,
   `alejandra.toml` (already correct), and the `secrets/`
   directory (atuin_key.txt, authorized_keys, k3s.yaml, proton.yaml).
   The `secrets/atuin_key.txt` and `secrets/proton.yaml` are
   referenced by the user NixOS module via relative path from
   `modules/aspects/users/`.

4. **Step 3 — host data dir.** Copy `facter.json` (already there),
   `host-seed`, `secrets/default.yaml`, `easyeffects/amesb fw16
   EE profile.json` from `~/nixos-config-baseline/systems/x86_64-linux/tide/`
   to `~/nixnew/hosts/tide/`. Copy `rfkill-wlan0.nix` to
   `~/nixnew/hosts/tide/rfkill-wlan0.nix`. Write
   `~/nixnew/hosts/tide/default.nix` with the per-host data attrs
   (mirroring source: the file is essentially a placeholder; the
   host aspect pulls data via den's `{host}` context).

5. **Step 4 — port the simple NixOS aspects first.** These are

   `modules/aspects/hosts/tide.nix` with `den.aspects.tide.nixos.imports`

    `modules/aspects/home/`:
    - `env.nix`, `shell.nix`, `dev.nix`, `rust.nix`,

    `den.aspects.m00n.includes = [<home/default>]` or similar

    actually gets applied. Verify
    `nix eval .#homeConfigurations."m00n@tide".config.home.username`

13. **Step 12 — flake check.** `nix flake check --no-build` should
    succeed. `nix build .#nixosConfigurations.tide.config.system.build.toplevel`
    should produce a NixOS toplevel derivation (the build will
    likely fail due to the new nixpkgs removing options the
    source's module options reference, but the **derivation** must
    evaluate cleanly).

14. **Step 13 — MIGRATION.md.** Write a short `MIGRATION.md` at
    the repo root documenting:
    - The aspect pattern used (flat `den.aspects.*` at top level;
      no namespace, no angle-bracket includes).
    - The deliberate port deviations (option path renames,
      `m00nlit.*` → `den.*`, list reordering, etc.).
    - The TODO about re-adding `stable` input + `pkgsStable`
      aspect when needed.
    - That the source's `nixos-config` itself doesn't build
      against current nixpkgs; the den port inherits the same
      upstream option breakage and inherits the same fix-by-future
      versions.

## Verification

- `nix flake check` returns 0 (no eval errors).
- `nix eval .#nixosConfigurations.tide.config.system.stateVersion`
  → `"26.05"`.
- `nix eval .#homeConfigurations."m00n@tide".config.home.username`
  → `"m00n"`.
- `nix build .#nixosConfigurations.tide.config.system.build.toplevel
  --dry-run` (so we don't actually build but verify the drv
  evaluates).

We do **not** verify "exactly identical" against the baseline.
That goal was previously deemed infeasible because the source
itself doesn't evaluate cleanly against current nixpkgs. The
port is faithful at the **module-source level** (option-for-option
translation); divergence is documented.
